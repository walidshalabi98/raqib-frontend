# Raqib — web app

The web app for Raqib (رقيب), an M&E platform for NGOs, INGOs and consultancies in Palestine and the region. The API lives in [raqib-backend](https://github.com/walidshalabi98/raqib-backend).

Stack: Vite 7 · React 18 · TypeScript · Tailwind 3 · shadcn/ui (Radix) · TanStack Query · React Router · react-hook-form + zod · Recharts · Leaflet · Vitest. Originally generated with Lovable.

## Quick start

Requirements: Node 22 and a running backend (see the backend README).

```bash
npm ci
echo "VITE_API_URL=http://localhost:3001/api" > .env.local   # optional; this is the default
npm run dev                                               # http://localhost:8080
```

The sign-in form starts empty. In development, sign in with an account from the backend's dev seed, for example `admin@momentumlabs.ps` (its password is `admin123` only under `NODE_ENV=development`; see the backend README).

> The dev server listens on `::` (IPv6). On machines without IPv6 run `npx vite --host 127.0.0.1`.

## Configuration

| Variable | Notes |
|---|---|
| `VITE_API_URL` | backend base URL including `/api`, e.g. `https://api.example.org/api`. Set per environment in Vercel. |
| `VITE_EMAIL_ENABLED` | `true` once the backend sends email (`RESEND_API_KEY` set there); unset or anything else means email is off. While it is off, "Forgot password?" says that reset by email is not available yet and to ask the organisation's admin, and the team screens say that the admin hands over a temporary password. Flip it in Vercel (and redeploy) when email is switched on. |

## Deployment (Vercel)

`vercel.json` routes every path to the app and sends security headers, including a Content-Security-Policy. `connect-src` currently allows any `https:` host. Once the production API address is fixed, replace `https:` with that address.

Until the public launch the site stays out of search engines: every response has the header `X-Robots-Tag: noindex, nofollow` (`vercel.json`) and `index.html` has `<meta name="robots" content="noindex, nofollow">`. `public/robots.txt` allows crawling on purpose: a crawler that may not fetch a page never sees its noindex, and could list a linked address anyway. Remove the header and the meta tag at launch (they apply to every deployment of the Vercel project). The favicon is `public/favicon.svg` (the Raqib monogram), with `public/favicon.ico` (16, 32 and 48 px) and `public/apple-touch-icon.png` (180 px) for browsers and phones that do not use SVG icons.

## Continuous integration

`.github/workflows/ci.yml` runs on every pull request and on `main`: install, lint, typecheck, tests, build, a check that the main bundle stays under 500 kB, and `npm audit --audit-level=critical`.

Known audit findings: Tailwind 3 depends on `chokidar`/`micromatch`/`braces`, and no patched version of `braces` exists. These are build-time tools and are not shipped to browsers. Removing them means moving to Tailwind 4 and dropping `lovable-tagger`, which itself depends on Tailwind 3. The owner accepted these 5 high findings (12 October 2026) until the Tailwind upgrade planned in Phase 6.

## KPI Assistant (Phase 4)

The KPI Assistant suggests indicators for the results chain (spec: `raqib-backend/knowledge/kpi-assistant-spec.md` Part A). It lives on the project's **M&E Framework** tab, inside the results chain panel:

- **Suggest KPIs** in the panel header (all results) and on each goal, outcome and output row. Activities get no button.
- Suggestions appear as cards under their result. **Accept**, **Edit & accept** (the indicator form, pre-filled from the suggestion; only the fields you change are sent; status, current value, actual dates and milestones are not part of a suggestion and are set after accepting), **Reject** (pick a reason, then confirm) and **Show alternatives**. Accepting an alternative to an indicator that is still in the framework first asks **Replace the old indicator?**: **Replace** removes the old indicator (only while it has no data or linked services), **Keep both** adds the new one next to it; in **Edit & accept** the same choice is a "Replace … with this indicator" tick box. The source badge shows a donor or standard code only for library indicators: an AI-written indicator without a library entry is always **Custom**.
- While suggestions are prepared, named steps show the progress. A run is followed for 2 minutes (all results: 10 minutes), counted on your own clock, then "This is taking longer than expected" offers **Refresh**. A finished run is announced to screen readers ("3 suggestions ready for O1", or "… across all results"). A run that finds nothing says so ("No new suggestions", or "No alternatives found" for alternatives); when nothing fits because of the level or the donor limit, the message says which. When an hourly limit is reached, the message says whether it is your own limit of AI requests or your organisation's limit of KPI suggestions, and offers no **Try again** (the limit lasts until the hour has passed); a short per-minute limit keeps **Try again**.
- After you add a goal, outcome or output, a prompt offers suggestions for it. Nothing is sent to the AI until you click; **Not now** hides the prompt for this session.
- Each result's indicator count opens its indicators, with their source, the AI label and a quality badge. An indicator with quality problems offers **Show alternatives**.
- The indicator table has a **Source** column. AI-made indicators keep the "AI suggested — review before approval" label (in the Table and Timeline views) until an org admin approves that indicator; an indicator accepted after the framework was approved keeps it too. Org and platform admins get an **Approve** button on every unapproved AI-made indicator, whatever the framework status (a manual framework in draft included), and on every other unapproved indicator once the framework is approved or active.
- **Request alternative** in the AI KPI Builder review step uses the same assistant. The alternatives appear on the framework tab; the toast says whether they are still being prepared, how many are ready, or that none were found, and its **Open the framework** link opens the tab directly (`/projects/:id?tab=me-framework`; any project tab can be opened with `?tab=`).
- Donor viewers see none of the KPI Assistant UI.
- **Archived projects** are read-only (owner decision of 13 October 2026): org staff still see the suggestion cards, run progress, notes and quality badges, with the note "This project is archived: you can read these suggestions, but not accept or reject them", and get no **Suggest KPIs**, **Accept**, **Edit & accept**, **Reject**, **Show alternatives**, **Suggest again**, **Try again** or new-result prompt; the indicator table offers no **Approve**. The project page decides this once, from `useProjectAccess` (`IndicatorTable canEdit` → `ResultsChainPanel readOnly` → `KpiAssistantProvider readOnly`, whose context `writable` the KPI components read). When the project was archived in another tab, a KPI write the server refuses with 409 `project_archived` shows the archived message (`kpi.errors.project_archived`, the same text as `errors.projectArchived`), and the page fetches the project again, turns read-only and moves focus to the archived banner. Once an org admin restores the project, that message goes and the controls come back (`KpiAssistantProvider` drops the `project_archived` errors when the project is writable again; screenshot `restored-after-refusal-*`). Deleting a project also drops its cached KPI suggestions and runs and its frameworks' results chain and quality check (`projectScopedKeys`, `projectRelatedKeys` in `src/hooks/useProjects.ts`).
- Without an Anthropic API key on the backend, the panel says AI suggestions are not set up and the buttons stay visible but disabled. You can still add indicators by hand or from the library.

Code: `src/components/kpi/` (cards, progress, provider), `src/hooks/useKpiSuggestions.ts` and `useKpiAssistant.ts`, `src/lib/kpiSuggestions.ts` (pure helpers), `src/components/project/ResultsChainPanel.tsx` and `ResultIndicatorList.tsx`. Toast messages are written in the user's language, and the toaster follows the user's direction. The KPI components have axe checks in English and Arabic (`src/components/kpi/KpiAccessibility.test.tsx`, `axe-core`; colour contrast is checked on the screenshots, which jsdom cannot do). `src/pages/ProjectDetail.kpiArchive.test.tsx` runs the real project page with the KPI Assistant on active and archived projects. Screenshots in English and Arabic at 375 px and 1440 px are in `docs/screenshots/phase4/` (suggestion cards, framework progress, Edit & accept, reject reasons, alternatives, AI not set up, indicator table with the AI label and Approve, and the panel on an archived project), taken with Playwright against the production build (`vite preview`) with the API mocked in the browser and made-up data, with axe (WCAG 2.2 AA) reporting no violation on any of them.

The backend's real evaluation of 14 October 2026 (`npm run eval:kpi` from the GitHub Actions button, prompt `kpi-v2`, model `claude-sonnet-5-5`, keyword retrieval) passed every gate of spec §A8: 8/8 cases, 53 suggestions, assertions 59/59, library use 81%, average quality 100, no hallucinated figures, no invented baselines, 29/29 calls, latency median 9.0 s and max 12.8 s, US$0.70 (backend `docs/AI.md` §12). The Phase 4 tables are in the staging database (applied 14 October 2026 with the owner's approval). The frontend needs no new Vercel variable for Phase 4.

## Working on Raqib

Read [`CLAUDE.md`](CLAUDE.md), [`docs/BUILD_GUIDE.md`](docs/BUILD_GUIDE.md) and [`docs/UX_STANDARDS.md`](docs/UX_STANDARDS.md) before changing screens.

- **Roles:** role-aware UI uses `can(role, capability)` from `src/lib/permissions.ts`, a mirror of the backend role matrix (backend `docs/SECURITY_SETUP.md` §8; keep both in step). The server enforces every rule; the UI only hides what a role cannot use. Pages read the role with `usePermissions()` and pass props such as `readOnly`, `canManage`, `canGenerate` or `audience` to components. The role comes from the current access token (`src/lib/session.ts`), the one the server reads, so a role an admin changes reaches the screens with the next token refresh (at most 15 minutes) without signing in again; `AuthProvider` then drops every cached response, because the API answers donor viewers in another shape. Missing or unknown roles get nothing (the donor view), and donor viewers never see beneficiaries' personal data or unreviewed AI output.
- **Expired sessions:** `src/services/api.ts` answers a 401 by refreshing the access token once (requests that expire together share one refresh) and repeating the request. The repeated request's answer is handled like any other, so a 409 or 422 keeps its `code` and `details` for the screen; the user is signed out only when the refresh fails or the repeated request gets 401 again.
- **Reports to donors:** every report starts as a draft that only staff see. The reports list (project Reports tab and the Reports page) shows staff each report's status as text and icon (Draft / Published to donors). Each finished report opens in a reading view (`ReportReader`) that shows its AI-written narrative in a sandboxed frame (no scripts, no network requests: `reportFrameDocument` in `src/lib/reports.ts`), labelled "AI written — review before publishing" while it is a draft. Org admins and platform admins (`report.publish`) publish only from that view, once the text is on screen, after a confirmation that says what donors will see; they can unpublish from the row or the view (`PATCH /api/reports/:id/publish` and `/unpublish`, `src/hooks/useReports.ts`). Donor viewers receive published reports only and read them in the same view. Staff generate a report with a title, type, donor format and optional period (`GenerateReportDialog`, react-hook-form with the zod schema in `src/lib/reportForm.ts`).
- **Sign-in and passwords:** `/` is the sign-in screen (nothing pre-filled; `autocomplete` set for password managers) with "Forgot password?" on the same card; `/login`, the address in older invitation emails, redirects there. The Forgot password form always answers with the same message whatever the server knows, so it never tells who has an account; while email is off (`VITE_EMAIL_ENABLED`) it says instead that reset by email is not available yet and to ask the organisation's admin. The "password changed" notice after a reset is shown once (cleared from the history state, announced, focus on the heading), and a reset ends any session the browser had. `/reset-password?token=…` (the emailed link, no sign-in) moves the token out of the address bar into the history state at once, asks for the new password twice, and sends the user to sign in with a notice; an invalid, expired or used link says so and offers a new one. Settings has Change password for every role; the server ends the account's other sessions and this one continues with the token pair it returns. The rules mirror the backend policy (`src/lib/passwordPolicy.ts`: 10 to 200 characters in their Unicode NFC form, not the current password, not the email's local part, at least 4 different characters, not a common password and not the product's or organisation's name, with the same 118-entry list as the server) and the server's refusals are shown from their `code` in English or Arabic, never as the server's English text. Every password field has a "Show password" toggle. The screens before sign-in set `<html lang dir>` and the page title in the chosen language, and their language switch has 44 px targets. Calls before sign-in (`login`, `forgotPassword`, `resetPassword`) send no token and pass a 401 on to the screen instead of signing out. A signed-in call that gets 401 refreshes once and sends the request again: only a refused refresh or a second 401 signs the user out; any other answer (400, 403, 409…) reaches the screen, and a refresh that is rate limited (429), fails on the server or gets no answer keeps the session and says to try again. The screens before sign-in follow the browser's language and have an English / Arabic switch.
- **Temporary passwords:** org admins and platform admins invite users and reset another member's password (Settings → Team members; `users.resetPassword` and `canResetPasswordOf` in `src/lib/permissions.ts`: never their own, and a platform admin's only as a platform admin), after a confirmation. While email is off, or when the email failed, the API returns the temporary password once (`temporaryPassword`). The mutation function hands it straight to `PasswordHandoverProvider` (mounted above the routes in `src/App.tsx`), so it is shown even if the admin left Settings while the request ran, and it never enters the mutation state or the query cache. `TemporaryPasswordDialog` shows it with a copy button, in groups of four for reading aloud, and the warning (shown only once; share it privately; ask them to change it after signing in). The focus starts on Copy password; a click outside and Escape do not close it; Done asks first when the password was not copied; closing or reloading the tab asks for confirmation while it is open. It is never logged or stored. With email on, the API emails a single-use link to choose a password and the screen only confirms. The Reset password row action keeps its visible label on phones.
- **Archiving and deleting projects** (owner decision of 13 October 2026): the Projects page has an Active projects / Archived projects switch (tabs, arrow keys; `?view=archived` in the address); the API leaves archived projects out of `GET /api/projects` and lists only them with `?archived=true` (`useProjectList` in `src/hooks/useProjects.ts`), so the Reports, Assessments and Beneficiaries pages offer active projects only. Archived projects carry an "Archived" badge (text and icon). On a project page, org admins and platform admins (`project.archive`, `project.delete`) get a "Project actions" menu: **Archive project** (a confirmation that says it leaves the active list, turns read-only, deletes nothing and can be restored), **Restore project** (also on the archived banner) and **Delete permanently** (says it cannot be undone, lists what goes from the counts the page already has, suggests archiving instead, and keeps the delete button off until the exact project name is typed, capitals included; the server checks it again and its refusals are shown in the dialog). After deleting, the app returns to the projects list with a confirmation. An archived project page shows a banner (`role="status"`, text and icon) and is read-only for everyone: the page derives every write control from one flag set, `useProjectAccess` (`src/lib/projectAccess.ts`: the role's capabilities, with `PROJECT_WRITE_CAPABILITIES` off while archived), and the AI framework wizard sends users back to the project. Reading stays: documents, reports, assessments, exports and the risk analysis. A write the server refuses with 409 `project_archived` (archived elsewhere meanwhile) is explained in the user's language (`errors.projectArchived` through `errorMessage` and `apiErrorText`, and in the toasts of the indicator and result forms, whose dialogs close as the page turns read-only), and the open project page fetches the project again, turns read-only and moves focus to the archived banner when the closed form left it nowhere (`src/lib/projectEvents.ts`). The Overview timeline shows no stage for an archived project (any project can be archived, from setup on), with an "Archived" note (text and icon); the current stage carries `aria-current="step"`. Archive and restore move the project between the cached active and archived lists at once and delete takes it out of them (`moveBetweenProjectLists`, `removeFromProjectLists`), so a list shown next never offers a project in the wrong view or one that is gone while it refetches; they also refresh both project lists, the project, the organisation overview and the project dashboard. Delete also drops the project's cached data and refreshes the notifications (`queryKeys.notifications`, shared by the bell and the activity feed), as the server deletes the project's notifications too.
- **Project tabs in the address:** `/projects/:id?tab=reports` opens the Reports tab (the Reports page links there; the backend's report notifications too); switching tabs updates `?tab=`.
- **Project dashboard:** `GET /api/dashboard/projects/:id/dashboard` (`useProjectDashboard`). Staff and donor viewers get the same keys; donor trends carry survey results as monthly aggregates (`surveyAggregates`, plotted by `src/lib/trends.ts`). Each indicator card's progress bar follows the backend's `indicatorProgress`: (current − baseline) / (target − baseline), also for indicators to reduce; current / target only for an output or activity count with no baseline; no bar otherwise. `src/services/api.paths.test.ts` pins the dashboard and report paths to the backend's routes.
